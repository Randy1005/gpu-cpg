# Strip24 full-suite comparison

## Verdict: no additional hybrid selector is needed on this evidence

Under the user's stated tolerance for small absolute regressions on fast cases,
keep the simple Strip24-enabled path rather than adding another graph/step
selector. There are 31 lower median times, including 26 speedups of at least
1.03x, and 12 higher median times. All regressions are below 3.4%; the largest
absolute regression is 0.868 ms (original des_perf). The largest percentage
regression is 3.38%, or 0.401 ms (leon3mp x8). Even the comparatively slower
netcard d50 baseline loses only 0.483 ms, or 0.45%.

By contrast, leon3mp d30 saves 60.757 ms, vga_lcd d40 saves 56.343 ms,
leon3mp d10 saves 54.041 ms, netcard d20 saves 47.750 ms and des_perf d30 saves
47.187 ms. A prospective selector would have to recover the small losses while
not reducing these gains or imposing costs on every step. Nothing measured here
justifies that additional complexity yet. This is a suite-supported engineering
decision, not proof that unseen graphs cannot regress.

The format is already selective locally: eligible one-parent slices become
24-byte records, existing multi-parent work keeps its 204-byte descriptors,
and rejected candidates remain ordinary nodes. This recommendation is against
an **additional** dispatcher, not against that existing representation mixture.
No benchmark-name heuristic or new adaptive threshold was introduced. The code
still defaults to the prior behavior; use `GPUCPG_STRIP24=1` to select the tested
extension. This benchmarking task does not change the production default.

New large wins correspond to real packed populations: netcard d20 represents
187,069,083 LONG paths in 7,627,528 strips; leon3mp d30 represents 100,302,593 in
3,728,942; des_perf d30 represents 242,565,066 in 9,468,632; and vga_lcd d40
represents 206,781,706 in 7,951,347. Only about 0.24–1.50% of those packed paths
later promote. These are cumulative created populations, not peak resident
counts or measured DRAM bytes. The producer/count change remains an attribution
caveat: this is the measured integrated pipeline, not a pure storage-only ablation.

Small absolute losses on already-fast cases do not by themselves justify a new dispatcher. Promotion fractions are retrospective evidence, not information assumed known by a prospective policy. The implementation also changes count aggregation, so this experiment does not isolate compression from producer changes.

## Correctness and measurement boundaries

All 86 pre-timing variant/case validations and 258 timed queries must pass the GPG K-cost golden comparator before this report is generated. The comparator uses 1e-3 absolute + 1e-6 relative tolerance; it is not bitwise equality. Existing corrected goldens are reused; missing ones are generated by GPG.

Descriptor classification, allocation/growth, creation, accounting, promotion and fallback costs are inside PFXT. Static setup is added per trial before taking the median. No new memory pool is enabled. GPU occupancy checks occur before each query, not continuously. Sub-percent differences should not be interpreted as established gains.

Raw matrix: `experiments/strip24-full-20260910-v2`. CSV is produced by `scripts/summarize-strip24-suite.py` using the same directory.

## Audit and reproduction

The runner exited successfully with `FULL SUITE COMPLETE`. An independent log
audit verified all 344 variant queries (86 initial validations + 258 timed
queries), with no retry, overflow or count-mismatch errors. All 43 goldens are
present; 13 were reused and 30 generated by GPG. The GPU unit test passed.
SHA-256 checks confirm the benchmark binary, main implementation and Strip24
header remained unchanged through the suite. The GPU was idle at completion.

[Full-precision CSV](strip24-full-20260910.csv) includes cold setup + PFXT,
separate setup/PFXT diagnostics, full query times and descriptor counts. The
report above uses cold setup + PFXT exclusively for its headline comparisons.
Median sums are computed per trial, rather than adding independently rounded
component medians.

From the `strip24-production` worktree, after the build instructions in
[the implementation report](strip24-production-20260910.md):

```sh
python3 -u scripts/run-strip24-full.py \
  --data /path/to/reproduction/csrbin \
  --goldens /path/to/corrected/goldens \
  --out experiments/new-strip24-full-run
python3 scripts/summarize-strip24-suite.py experiments/new-strip24-full-run
python3 scripts/report-strip24-full.py experiments/new-strip24-full-run
```

The runner requires a new output directory, checks GPU compute-process idleness
before each query, clears inherited `GPUCPG_*` flags, reuses available goldens,
generates missing ones, and validates the entire suite before timing. Any query
error terminates the run. The generated report provides the data; the interpretation
and recommendation above are specific to this completed run.
